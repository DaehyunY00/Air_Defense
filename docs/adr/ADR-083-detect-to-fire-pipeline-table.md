# ADR-083 — [분석] 탭 시간표를 「탐지→발사 파이프라인」 한 장으로 합치고, 승인 오분류를 바로잡는다

- 상태: 채택
- 일자: 2026-08-03
- 관련: ADR-076([분석] 탭 개편) · ADR-058(승인 계선) · ADR-071(자위권 발사) · ADR-081(결심시간 분해 — **이 ADR로 대체**)
- 성격: **순수 후처리·UI 개편.** 엔진·RNG·`_mark`·이벤트 순서 불변 → SHA-256 비트 기준선 영향 없음

## 배경 — 시간표가 두 장이었고, 서로 맞지 않았다

[분석] 탭에는 시간표가 둘이었다.

| | 함수 | 기준점 | 코호트 | 관문 |
|---|---|---|---|---|
| ①-2 「C2가 실제로 쓴 시간 — 결심시간 분해」 | `decisionSplit` (ADR-081) | 탐지 | 3관문(detect·prep·assign) | 3구간 |
| ② 「어디서 벌어졌나 — 구간별 소요시간」 | `gateStats` (ADR-076) | 침투(생성) | 6관문(spawn·detect·fuse·ident·assign·fire) | 6구간 |

기준점도 코호트도 다르니 **정의가 같은 구간조차 숫자가 달랐다**. 그래서 읽는 사람이
"어디서 문제가 생겼고 어디서 개선됐나"를 한 화면에서 판단할 수 없었다.

## 진단 — 소스에서 확인한 사실 넷

`js/engine/sim-engine.js` 기준.

1. **`위협판단·표적할당준비:`와 `식별확정:`은 항상 같은 시각이다.** 둘 다 책임 C2 노드의
   `_nodeArrive` 완료 콜백에서 연속으로 찍힌다(sim-engine.js §`_onIadsC2Arrive`,
   `식별확정:` 바로 다음 줄이 `위협판단·표적할당준비:`). 실측 SC3: 두 마크가 다 있는 247건
   **전부** 소수점 아래까지 동일. 게다가 `식별확정:`은 센서물리 계측이 켜졌을 때만 찍힌다 —
   관문으로 두면 **표본만 좁아지고 재는 것은 없다.**
   → 구 ①-2의 ①(탐지→준비) = 구 ②표의 ②(탐지→융합) + ③(융합→식별확정),
     구 ①-2의 ②(준비→선정) = 구 ②표의 ④(식별→선정). **정의가 이미 겹쳐 있었다.**
2. **코호트가 달라 겹치는 구간의 평균이 어긋났다.** 실측 SC3: 같은 「준비→선정」 구간이
   `decisionSplit` 코호트(67건)에서 As-Is 57.94초, 새 단일 코호트(57건)에서 65.82초.
3. **합계의 기준점이 달랐다.** ①-2 합계는 탐지→사수선정, ②표 합계는 침투→발사.
4. **승인계선 시간이 오분류돼 있었다.** `_iadsApprovalGate`는 `위협판단·표적할당준비:` 마크
   **이후** `_iadsDecide` 안에서 돈다(sim-engine.js `_iadsDecide` → `approvalChain &&
   commander.axis === 'LOCAL_AD'` 분기). 따라서 LOCAL_AD 축(육군 국지방공)의 음성협조·승인
   큐 시간은 실제로는 구 ①-2의 **②**에 들어가 있었다 — 「C2 성능이 아님」이라 설명하던
   그 구간이다. ①의 라벨 「…위협평가·**승인**까지」는 **사실이 아니었다.**

추가로 확인한 것: `책임C2:`는 센서 **보고** 이벤트에서 찍히는데 대개 탐지와 같은
이벤트다(302건 중 290건 동일, 어긋나는 12건도 보고 틱 0.2~5초). C2가 일한 시간이 아니므로
관문으로 쓰지 않는다(ADR-076의 판단 유지 — 다만 "항상 0초"는 과장이었으므로 표현을 고쳤다).

## 결정 — 「탐지 → 발사 파이프라인 시간표」 한 장

### 기준점

**0초 = 탐지.** 침투→탐지는 센서 물리이며 CRN 설계상 양 모드가 동일하다. 그 사실을 버리지
않고 **회색 참고행**으로 맨 위에 남긴다 — (a) 양 모드가 같다는 것이 곧 짝맞춤이 공정하다는
증거이고, (b) 절대 시각 감각을 준다. 비교 대상은 아니다.

### 구간 (전부 기존 `stages` 마크의 후처리 — 엔진에 새 마크를 넣지 않았다)

| # | 구간 | 관문 (from → to) | 성격 배지 |
|---|---|---|---|
| 참고 | 침투 → 탐지 | `생성` → `탐지` | 센서 물리 (회색·비교 제외) |
| ① | 탐지 → 항적 융합 | `탐지` → `항적융합:` | **C2 입력** |
| ② | 융합 → 식별·할당준비 | `항적융합:` → `위협판단·표적할당준비:` | **C2 처리** |
| ③ | 승인 · 협조 | first(`협조개시:`\|`감독승인개시:`) → first(`승인완료:`), 없으면 **0초** | **C2 구조** |
| ④ | 사격통제 성립 대기 | **잔여** = (`위협판단·표적할당준비:`→`사수선정·표적할당:`) − ③ | **물리·조율** |
| ⑤ | 선정 → 발사 | `사수선정·표적할당:` → `발사:`\|`자위권발사:` | **C2 출력** |
| ⑥ | 합계 | `탐지` → `발사` | — |

`gateT`에 `approveStart`·`approveEnd`·`deleg`·`dedup`·`selfdef` 종류를 추가했다. **엔진에는
손대지 않았다** — 승인 시간은 이미 기존 마크에 전부 찍혀 있고, 자기승인 축(KAMDOC·MCRC)과
동적 `권한위임:`은 **마크가 없는 것이 곧 "대기 0초"라는 사실**이다.

### ③/④ 분리 규칙 — 창 클램프와 잔여 정의

③은 timestamp가 아니라 **구간 길이**다. 다만 그 구간을 `[prep, assign]` 창에 **겹치는
몫만** 계상한다:

```
③ = max(0, min(승인완료, 선정) − max(협조개시, 준비))
④ = (선정 − 준비) − ③
```

클램프가 필요한 이유는 한 항적에 지휘 축이 **동시에 여럿** 붙기 때문이다(통합축 KILL_WEB +
국지축 LOCAL_AD). 승인을 기다리던 축이 아닌 쪽이 먼저 사수를 선정하면 승인 구간이 창 밖으로
삐져나간다 — 실측 SC3 코호트 114(항적×모드) 중 **9건**이 그렇다(5건은 완전히 창 밖, 4건은
부분). 클램프하지 않으면 **④가 음수인 칸이 표에 나온다.**

④를 **잔여**로 정의했으므로 **①+②+③+④+⑤ ≡ ⑥**이 항적마다 항등으로 성립한다
(실측 최대오차 1.1e-13). 부분의 합이 합계와 어긋나는 사고가 구조적으로 불가능해졌다.

### 코호트 — 하나뿐

탐지→발사 전 관문(spawn·detect·fuse·prep·assign·fire)을 **양 모드 모두** 통과한 항적 하나로
모든 행을 계산한다. **③의 승인 마크는 코호트 조건이 아니다** — 마크 부재는 제외가 아니라
0초다(실측 114건 중 81건). 제외 건수를 화면에 공시한다.

대가: `decisionSplit`이 잡아주던 "사수선정까지 갔지만 발사에 못 간 항적"이 시간표에서
빠진다. 이는 「여기까지 온 항적」 열과 ③ 항적 로그 카드가 담당함을 각주로 안내한다.

### 컬럼

1. **구간 소요** As-Is / To-Be / Δ
2. **탐지 후 누적 도달 시각** As-Is / To-Be / Δ — **주 지표**(단조 증가라 부호가 안 뒤집힌다)
3. **여기까지 온 항적** — 짝지은 **전** 항적 기준 도달 수(중간 탈락 공시)

## 검증 — SC3 · LEGACY_NORMAL · 기본 플래그 · seed 12345 · 900초

코호트 57건 (짝지은 157건 중 100건 제외).

| 구간 | 성격 | 구간 소요 As-Is → To-Be | 누적 도달 As-Is → To-Be |
|---|---|---|---|
| 참고 침투→탐지 | 센서 물리 | 4.03 → 4.03초 (**Δ 0.00 — CRN 공정성 증거**) | 기준점 |
| ① 탐지→융합 | C2 입력 | 2.58 → 0.80초 (Δ −1.77) | 2.58 → 0.80초 |
| ② 융합→식별·할당준비 | C2 처리 | 29.15 → 2.15초 (Δ **−27.00**) | 31.72 → 2.95초 |
| ③ 승인·협조 | **C2 구조** | 14.57 → 0.74초 (Δ **−13.84**) | 46.30 → 3.69초 |
| ④ 사격통제 성립 대기 | 물리·조율 | 51.25 → 90.21초 (Δ **+38.96**) | 97.55 → 93.90초 |
| ⑤ 선정→발사 | C2 출력 | 8.90 → 6.78초 (Δ −2.12) | 106.44 → 100.68초 |
| **⑥ 합계 탐지→발사** | | **106.44 → 100.68초 (Δ −5.76)** | 동일 |

승인 계선을 실제로 경유한 항적: As-Is 15건 → To-Be 13건. 교전중복해소 마크 보유:
As-Is 0건 · To-Be 26건. 자위권 발사(사수선정 없이): As-Is 16건 · To-Be 0건.

### 구표 검산 (같은 코호트로 재계산 — 전부 1e-9 이내 일치)

| 구 지표 | 구 값 | 새 표 대응 | 새 값 |
|---|---|---|---|
| 구 ①-2의 ① (탐지→준비) As-Is | 31.723초 | ①+② | 31.723초 |
| 구 ①-2의 ① (탐지→준비) To-Be | 2.954초 | ①+② | 2.954초 |
| 구 ①-2의 ② (준비→선정) As-Is | 65.824초 | ③+④ | 65.824초 |
| 구 ①-2의 ② (준비→선정) To-Be | 90.946초 | ③+④ | 90.946초 |
| 구 ②표 합계 (침투→발사) | — | 참고행 + ⑥ | 일치 |

**구 ①-2의 원(原) 코호트(67건)** 로 뽑으면 ① 32.89→3.46초 · ② 57.94→83.20초로, 같은 정의의
구간인데도 값이 다르다. 이것이 §진단 2가 말한 코호트 불일치이며, 통합의 직접 동기다.

### 새로 보이게 된 것

구 표에서는 「준비→선정 65.8초(As-Is)」가 통째로 「C2 성능이 아닌 물리 대기」로 설명됐다.
분해하면 그 중 **14.57초가 승인·협조(사람 채널)** 이고 51.25초가 물리다. To-Be에서 승인은
**0.74초로 −13.8초** 줄었다 — 이것은 **C2 구조가 만든 이득**이지 물리가 아니다.
구 서술은 이 이득을 물리 대기 항목 안에 숨기고 있었다.

동시에 정직하게 남는 사실: ④는 As-Is 51.25 → To-Be 90.21초로 **+38.96초 늘었다.** 상류
(①②③)를 앞당길수록 위협이 교전 가능 위치로 날아올 때까지 더 기다리기 때문이다. 그래서
합계(⑥)의 이득은 −5.76초에 그친다. **④를 C2 성과로 쓰지 않고, ④에 승인 외 조율 대기
(교전중복해소·COP)가 섞여 있음도 숨기지 않는다** — 두 사실 모두 표 각주에 공시한다.

> 위 수치는 **실제 렌더러**(`KJ.panels.renderAnalysis`)를 최소 DOM 스텁 위에서 돌려 뽑은
> 표 본문에서 그대로 옮긴 것이다 — 후처리기만 따로 호출한 값이 아니라 **화면에 나가는 값**이다.
> (브라우저 스크린샷은 이 환경에서 확장이 붙지 않아 남기지 못했다.)

## 되돌리는 법

`js/ui/panels.js`의 `PIPE`·`pipelineStats`·`approvalSpan`을 지우고 ADR-076/081 시점의
`GATES`·`gateStats`·`decisionSplit`을 복원, `index.html`의 `analysis-pipeline` 컨테이너를
`analysis-decision`·`analysis-gates` 두 장으로 되돌린 뒤 단일본 재빌드. 엔진은 건드린 것이
없으므로 수치는 어느 쪽이든 동일하다 — 되돌리면 §진단의 오분류와 코호트 불일치도 함께
돌아온다.

## 하지 않은 것

- **엔진에 새 마크·새 계측을 넣지 않았다.** 기존 마크로 충분함을 §진단 4에서 확인했다.
- **구간마다 다른 코호트로 평균 내지 않았다.** 부분합≠합계 왜곡의 재발 경로다.
- **④를 C2 성과로 서술하지 않았다.** 동시에 ④가 순수 물리인 척하지도 않았다.
- **격추·누수 등 임무 지표를 이 표로 대체 서술하지 않았다.**

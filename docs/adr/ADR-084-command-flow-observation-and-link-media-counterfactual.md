# ADR-084 — 지휘 흐름을 계선 위의 움직임으로 관측하고, 계선 매체를 갈아 끼워 본다

- 상태: 채택
- 일자: 2026-08-11
- 관련: ADR-057·066(링크 의미론) · ADR-062(지표 정직성) · ADR-073(결심 감사) · ADR-078(병렬 통보) · ADR-080·082(사람 매개 채널 분포) · ADR-081(축별 레인) · ADR-083(탐지→발사 시간표)

두 건을 한 판에 묶는다. **①은 순수 관측이고 수치를 한 발도 움직이지 않는다.**
**②는 반사실 실험 장치이며, 켜면 실행 전체가 다른 표본이 된다.**

---

## ① 지휘 흐름 관측 `flowTrace` — 수치 불변

### 배경

이 모델은 계선의 성격을 **이미 수치로** 갖고 있다. 데이터링크 1~2초, 센서 보고주기,
KVMF 상급경유 30초, 음성 협조 정규(20, σ5), 문자 정규(45, σ7.5), 음성/VTC 정규(135, σ22.5)
— ADR-057·066·080·082가 하나씩 세워 온 것들이다.

그런데 **그 차이가 화면 어디에도 움직임으로 나타나지 않았다.** [분석] 탭 시간표(ADR-083)는
구간 합계를 숫자로 보여주고, [C2 구조] 탭은 계선의 존재를 선으로 보여준다. 둘 다
「이 전문이 지금 저 선 위를 기어가고 있다」를 보여주지 않는다. 발표에서 「음성 협조가
느리다」를 말로 설명하고 표로 증명해야 했다.

기술적 장애물은 하나였다. **엔진이 전문의 출발 시각을 남기지 않았다.**

- `_mark`(ADR-081)는 **도착 사건의 이름·시각·축**만 남긴다.
- `_linkDelay()`가 뽑은 지연은 `schedule()`에 쓰이고 **사라진다.**
- `_recordLink`는 통과 **횟수**만 센다(Little's Law 집계용).

그래서 「선 위의 점」을 그리려 해도 출발시각을 되살릴 수가 없었다.

### 결정

관측 채널 `flowTrace`(옵트인, 기본 false)를 둔다. 두 종류를 남긴다.

```
링크 통과   { k:'link', from, to, mt(매체), kind, t0(출발), t1(도착), d(실제 지연), nominal, th(항적) }
노드 체류   { k:'na', id, at, jk, th, t }   도착
            { k:'ns', id, t }               서비스 개시
            { k:'nd', id, t }               완료
채널 적체   { k:'cq', id, ch, from, to, t, th }        대기 진입 — 갈 곳은 정해졌는데 채널이 안 비어 못 떠남
            { k:'cx', id, ch, from, to, t, th, r }     용량 드롭 — 대기줄에도 못 서고 버려짐(영영 출발 안 함)
            link 이벤트의 `mid`가 cq와 출발을 잇는다

            { k:'nx', id, t, r }            이탈. r(사유)이 드롭 계정 대사의 열쇠다:
                                            · r='over' — 도착 즉시 대기실 초과 드롭 (ns.drops 계상)
                                            · r='ttl'  — 대기 중 기한 만료 드롭 (ns.drops 계상)
                                            · r='dead' — 항적 종결(격추·이탈)로 큐 정리 (드롭 아님)
                                            관측 종료 전에 끝난 체류는 반드시 nd 또는 nx로 닫힌다 —
                                            처음에는 reneging 두 경로가 nx를 안 남겨, 화면에서 그 노드가
                                            영원히 "대기 중"으로 굳었다(리뷰에서 발견·수정).

### 장부 대사 — 관측이 엔진과 맞물린다는 증명

flowTrace로 재구성한 수치와 엔진의 **독립 카운터**(결과 `nodes[].arrivals/completions/
drops/maxInSystem`)를 전 노드에서 맞춰 본다. 회귀(`flow-trace.test.mjs` ③-e~g)가 잠근 것:

| 관측 재구성 | = | 엔진 카운터 |
|---|---|---|
| na 건수 | = | arrivals |
| nd 건수 | = | completions |
| nx(over) + nx(ttl) | = | drops (dead는 큐 정리라 계상 안 됨) |
| max(busy+q) 재생 | = | maxInSystem |

재생 불변식(q ≥ 0 · busy ≤ c)도 함께 잠근다. 동률 시각의 순서는 엔진 실순서인
**완료 → 도착 → 개시 → 이탈**이다(서비스 종료가 서버를 비운 뒤 대기열에서 인출한다).
두 모드 + 고강도(×3, over 73건 발생 조건)에서 전 노드 일치를 확인했다 — 사수 노드만
결과가 교전자원 카운터(commandArrivals)를 보고하므로 비교 대상이 달라 제외한다.

이 대사가 있어야 「로그에 같은 문구가 여러 줄」이 **이중 기록이 아니라 서로 다른 사건**임을
말할 수 있다(사건 수 = 엔진 카운터이므로). 화면은 그 위에서 표시만 묶는다: 포화
진입/해소 쌍 → 구간 한 줄(지속시간·최대 대기), 넘침·기한·큐 정리 → 10초 이내 버스트
한 줄(×N + 대표 항적). 스크럽 눈금은 원사건 전량을 유지한다 — 축 위에서는 밀도가 곧 정보다.

### 「가야 할 방향은 있는데 못 가는」 것을 보이게 한다 (채널 적체)

종전 관측에는 **더 큰 구멍**이 있었다. `_recordLink`는 **실제로 출발한 전문만** 기록하므로,
교전현황 채널(군단 AOC → MCRC · 음성/VTC **1채널·4건**)의 용량에 막혀 대기하거나 버려진
전문은 흔적조차 없었다. 실측이 그 심각성을 보여준다:

| SC3 · seed 12345 · 600초 | 보냄 | 도착 | 드롭 | 대기 |
|---|---|---|---|---|
| As-Is ×1 | 15 | **2** | 5 | 8 |
| As-Is ×3 | 48 | **3** | 38 | 8 |
| To-Be ×1 | 18 | 17 | 0 | 0 |

**보낸 15건 중 2건만 건너가는데 화면에는 그 2건만 보였다.** 못 간 13건이 As-Is 병목의
본체인데 관측에서 통째로 빠져 있었던 것이다.

`cq`(대기 진입)·`cx`(용량 드롭)를 남기고, `mid`로 대기와 출발을 이어 **언제부터 못 갔는지**를
되살린다. 화면은 계선 **입구에 줄 세워** 그린다 — 채운 원(이동 중)이 아니라 **점선 빈 원**이고
시각이 흘러도 제자리다. 관측 종료까지 못 간 것은 붉게 구분한다.
⚠️ 대기 **위치**는 표시 관례일 뿐 모델 좌표가 아니다(모델에 대기 위치 개념은 없다).
실재하는 것은 「언제부터 언제까지 못 갔는가」이며, 라벨·툴팁에는 그것만 적는다.

회귀(`flow-trace.test.mjs` ③-h)가 대사를 잠근다:
**즉시출발 + 대기(cq) + 드롭(cx) = statusSharing.sent**, 그리고 `cq`=queued · `cx`=dropped.
드롭 경로는 기본 설정에서 0건이라 증명력이 없으므로 **×3에서 별도로** 잡는다(실측 드롭 7건).

노드 케파(도넛 링)가 「처리 못 함」이라면 이것은 「**보내지도 못함**」이다 — 둘은 다른 병목이고,
화면에서 다르게 보여야 한다.
```

- **`d`는 대표값이 아니라 그 실행이 실제로 뽑은 값이다.** 그래서 같은 매체라도 건마다
  다르다(실측: 음성 협조 9.0~31.1초, 문자 22.3~72.6초). 화면의 점 속도가 곧 그 표본이다.
- 노드 체류를 `id`로 이어 붙여야 **대기(도착~개시)와 처리(개시~완료)가 갈린다.** 이 둘을
  합쳐 두면 As-Is 병목이 「느린 선」인지 「막힌 노드」인지 구분되지 않는다.

### 순수성 — 이 절이 이 ADR의 핵심이다

관측이 모델을 바꾸면, 그 화면에서 읽은 어떤 수치도 인용할 수 없게 된다. 그래서:

- **RNG를 뽑지 않는다.** 지연값은 호출부가 이미 뽑아 둔 것을 **넘겨받는다.**
  ⚠️ `_recordLink` 안에서 `_linkDelay`를 다시 부르면 난수를 한 번 더 소비해 실행이 갈라진다.
- **호출 순서를 바꾸지 않는다.** `_startIadsStatus`에서 `_linkDelay` 호출을 한 줄 앞으로
  당겼는데, `_recordLink`가 난수를 쓰지 않으므로 소비 순서는 그대로다.
- **병렬 통보(ADR-078)는 `linkStat`에 넣지 않는다.** 카탈로그에 실재하는 간선이 아니라서,
  집계에 섞으면 **flowTrace를 껐을 때의 결과 `links` 배열까지 달라진다.** 관측 채널로만 보낸다.
  대신 지연 0으로 **남기기는 한다** — 빼면 통보가 없었던 것처럼 보인다(ADR-062의 0/미측정 구분).
- **상한(기본 60000)을 넘으면 잘랐다는 사실을 남긴다**(`flowTruncated`).

### 실측

`SC3 · 한반도 본 배치 · seed 12345 · 600초`:

| | As-Is | To-Be |
|---|---|---|
| 링크 통과 | 1321건 | 964건 |
| 쓰인 매체 | datalink · report-cycle · internal · kvmf-relay · **voice · chat · voice-vtc** | ifcn · report-cycle · internal · fanout |
| 사람 매개 채널 | 있음 | **0건** |

한 항적(`uav_small#2`, As-Is)이 화면에서 이렇게 읽힌다:

| 구간 | 매체 | 걸린 시간 |
|---|---|---|
| 탐지 → MCRC 접수 (3홉) | 데이터링크 | 2.9초 |
| MCRC → 육군 방공상황실 3곳 | 문자(서버 채팅) | 31.2 · 38.6 · 45.6초 |
| 방공상황실 → MCRC 승인협조 | 음성 | 19.6 · 22.3 · 22.7초 |
| 승인 완료 | — | 92.6 / 108.4 / 116.5초 |

회귀 `tests/flow-trace.test.mjs`가 **ON/OFF 결과 SHA-256 일치**를 두 모드에서 잠근다.
전체 스위트도 통과했다(기준선 6케이스 포함).

### 부수 발견 — 화면이 모델을 잘못 그리고 있었다

프로토타입이 처음에 간선을 `(from, to)`로 유일화했다. 그런데 **방공C2A → MCRC 사이에는
성격이 다른 계선이 세 가닥 병렬로 있다**:

| 계선 | 매체 | 대표값 | 축 |
|---|---|---|---|
| 교전현황 공유 | 음성/VTC | 135초(1채널·4건) | `corps_aoc_engagement_status` |
| 승인 협조 | 음성 | 20초 | `corps_aoc_approval` |
| 항적 공유 | 문자 | 45초 | `corps_aoc_track_share` |

한 가닥으로 접히면 먼저 만난 매체의 색만 남아 **나머지 두 채널이 없는 것처럼** 보였다.
간선의 신원을 `(from, to, 매체)`로 고치고, 병렬 계선을 벌려 그린다. 회귀에도
「같은 두 노드를 잇는 성격이 다른 병렬 계선이 존재한다(5쌍)」를 못 박았다.

## ② 계선 매체 반사실 `linkMediaOverrides` — **실행이 다른 표본이 된다**

### 배경

「이 계선이 문자 대신 데이터링크였다면?」은 이 연구가 답해야 할 질문의 형태 그 자체다.
그런데 종전에는 그것을 보려면 배치 카탈로그를 고쳐 코드를 다시 빌드해야 했다.

### 결정

`KJ.withLinkMediaOverrides(catalog, overrides, mode)` — 특정 계선만 다른 매체로 갈아 끼운
**사본**을 만든다(캐시된 원본은 그대로). 엔진은 `cfg.linkMediaOverrides`가 있을 때만 쓴다.

```
overrides = { '<from>><to>><kind>': '<매체 키>' }
매체 키   = KJ.LINK_MEDIA_PRESETS의 것만  (datalink · ifcn · internal · voice · chat · voice-vtc · kvmf-relay)
```

- **임의의 초를 넣을 수 없게 둔다.** 근거 없는 숫자를 넣으면 그 실행의 결과는 인용할 수
  없는 것이 되는데, 화면에서는 그 구분이 보이지 않는다. 카탈로그에 실재하는 매체로만 바꾼다.
- **사전은 `deployment-adapter.js` 위쪽의 그 상수들 자체를 내보낸다.** 값을 다시 적으면
  두 벌이 되어, 위를 고쳐도 실험 쪽은 옛 값으로 조용히 남는다.
- **못 맞춘 키를 삼키지 않는다**(`unmatched`). 오타 하나로 「바꿨는데 안 바뀐」 실행이 나온다.
- 적용 내역을 `result.linkMediaOverrides`에 실어 **반사실이라는 사실이 결과를 따라다니게** 한다.

### ⚠️ 한계 — 짝맞춤이 깨진다

매체가 바뀌면 `_linkDelay`의 **난수 소비가 달라져 실행 전체가 다른 표본**이 된다. 같은
seed라도 그 이후의 모든 추첨이 어긋난다. 그러므로:

> 기준 실행과 반사실 실행을 나란히 놓고 **「차이 = 그 계선의 몫」으로 읽으면 안 된다.**

실측이 이를 그대로 보여준다 — 문자 계선 3가닥을 데이터링크로 바꾸자 `uav_small#2`의 승인
완료는 92.6/108.4/116.5초 → **82.1/84.8/96.0초**로 당겨졌지만, 전체 격추는 61 → 60,
누수는 22 → 25로 **오히려 나빠졌다.** 이것은 계선 개선이 해롭다는 뜻이 아니라, **한 판
비교로는 아무것도 말할 수 없다**는 뜻이다. 인과를 주장하려면 짝맞춤 Monte Carlo가 필요하며,
그것은 이 ADR의 범위 밖이다(후속 과제).

화면에도 이 경고를 팝오버마다 띄우고, 상단에 「반사실 N건 적용」을 상시 표출한다.

### ⚠️ 한계 2 — 매체를 바꿔도 채널 구조는 남는다

교전현황 status 채널은 링크 comm의 `messageServers`/`messageCapacity`로 만들어지는데,
없으면 **기본값 1채널·4건·신선도 300초**가 적용된다(`_initIadsResources`). 그래서 음성/VTC
(135초)를 데이터링크(1초)로 갈아 끼우면 **지연 분포만 바뀌고 1채널·4건 용량 제약은 그대로
남는다.** 서비스가 135배 빨라져 큐가 잘 안 차므로 실질 영향은 작지만, 방향은 분명하다 —
이 반사실은 데이터링크 전환의 효과를 **과소평가**한다(진짜 데이터링크라면 용량 제약 자체가
없어야 한다). 반대 방향(일반 계선을 voice-vtc로)은 용량 제약이 **생기지 않는다** — 채널
구조는 status 계선에만 존재하기 때문이다. 인용 시 이 비대칭을 함께 밝혀야 한다.

## 범위

- 화면은 `prototype/command-flow.html` **하나뿐이며 본 앱(index.html)에는 붙이지 않았다.**
  붙일지 여부는 이 프로토타입으로 쓰임새를 확인한 뒤에 정한다.
- 킬체인 열(센서 → 포대 교전통제 → 권역 교전통제 → 상급 C2 → 조율층 → 국지방공 C2 → 요격부대)은
  **[C2 구조] 탭의 지휘 계층(`tierOf`)과 축이 다른 별개의 표시 계약**이다. 같은 것의 두 벌이
  아니라 다른 것을 다르게 그리는 것이라, 중복 구현 금지 규율에 걸리지 않는다.
- 이 배치는 **완전한 좌→우 단방향이 아니다.** 승인 협조와 교전명령 하달은 왼쪽으로
  되돌아간다. 숨기지 않고 아래로 휘는 역방향 호로 그린다 — 되돌아가는 것 자체가 As-Is의 모양이다.

## 프로토타입에서 배운 함정 두 가지 (파일 주석에도 남김)

1. 워커·Node 진입점의 `globalThis.window = globalThis`를 브라우저로 옮기면 안 된다.
   `window`가 getter 전용이라 **모듈 전체가 조용히 죽는다**(콘솔에도 안 잡히고 화면만 빈다).
2. 재생 시계를 `requestAnimationFrame`으로 돌리면 안 된다. 탭이 배경으로 가면 rAF는 정지하고,
   재생 버튼은 눌린 채로 **시계만 멈춘다**(실측: 2.5초 동안 시각 불변). 타이머로 돌리고
   경과는 벽시계에서 잰다.

## 추기(2026-09-03) — 화면 기본 seed를 대표 표본(29)으로 바꾼다

**문제.** [지휘 흐름]의 기본 seed는 본 앱과 같은 12345였는데, **이 화면의 조건**
(SC3 · As-Is · 600초 · LEGACY_NORMAL · 화면 기본 플래그 pipe=1·icc=1·issue=0)에서 12345는
32개 seed 가운데 **가장 심한 이상치**였다.

| | seed 12345 | 32 seed 중앙값 |
|---|---|---|
| KAMDOC `iads_track` 도착 | **75건** | 50건 |
| KAMDOC ρ | **0.81** | 0.48 |
| As-Is 격추 / 누수 | 34 / **44** | 30 / 25 |
| `?issue=1`의 격추 Δ | **−20** (34 → 14) | −2.5 |

한 노드가 홀로 포화된 판이라, 이 화면으로 무엇을 읽든 그 성질이 묻어난다. 특히
`?issue=1`(ADR-096 교전명령 발령)을 켜면 격추가 34 → 14로 무너져 **「발령 비용을 켜면 격추가
반토막」이라는 잘못된 인상**을 준다 — 32 seed 평균 Δ는 −3.3, 16 seed 재기준선(ADR-096
§프로토타입 기본값)은 −3.1이다. 이 화면은 조건을 갈아 끼우며 **같은 판을 계속 보는** 도구이므로
(그것이 ADR-084 ①의 설계 의도다) 기본 표본이 대표성을 가져야 한다.

**선정 규칙**(사후에 「좋아 보이는 판」을 고르는 것을 막기 위해 먼저 정한 것): seed 1~31과
12345를 위 조건으로 돌려, ① As-Is 격추 ② To-Be 우위(To-Be 격추 − As-Is 격추) ③ `?issue=1`의
격추 Δ — 세 지표의 **중앙값 이격(정규화 절대편차)의 합이 최소**인 seed를 채택한다.

| 순위 | seed | As-Is 격추/누수 | To-Be 우위 | KAMDOC 도착 · ρ | `?issue=1` 격추(Δ) · 발령/드롭 | 이격 |
|---|---|---|---|---|---|---|
| **1** | **29** | **30 / 34** | **+18** | **53건 · ρ0.60** | **28 (−2) · 49건/3** | **0.36** |
| 2 | 30 | 29 / 23 | +18 | 47건 · ρ0.45 | 27 (−2) · 39건/0 | 0.40 |
| 3 | 8 | 25 / 25 | +15 | 49건 · ρ0.50 | 23 (−2) · 45건/0 | 0.40 |
| … | | | | | | |
| 32 | 12345 | 34 / 44 | +21 | 75건 · ρ0.81 | 14 (**−20**) · 46건/**14** | 7.49 |

(중앙값: As-Is 격추 30 · To-Be 우위 +15.5 · issue Δ −2.5)

**결정.** `prototype/command-flow.html`의 seed 기본값을 **29**로 바꾼다(화면 입력칸과 `PARAMS`
양쪽 — 단일본은 재생성). seed 29는 세 지표가 모두 중앙값 부근이면서 KAMDOC 큐가 실제로 차오르고
(ρ0.60) `?issue=1`에서 발령 드롭 3건이 나와, **이 화면이 보여주려는 것들이 전부 관측되는** 판이다.

> ⚠️ **본 앱(`js/core/router.js` DEFAULTS)의 seed는 12345 그대로다.** 두 화면의 기본 표본이
> 갈라지므로 같은 항적 번호(`srbm#9` 등)가 서로 다른 위협을 가리킨다. 시나리오(sc3 vs sc1)와
> 관측시간(600 vs 1800)이 이미 다르므로 새로 생긴 비대칭은 아니지만, 두 화면을 나란히 인용할
> 때는 seed를 명시해야 한다. 종전 판을 그대로 보려면 `?seed=12345`.
>
> ⚠️ 이 표는 **대표 표본을 고르기 위한 것이지 수치를 주장하기 위한 것이 아니다.** 한 판
> 비교로 인과를 말할 수 없다는 ADR-084 §한계는 그대로다.
